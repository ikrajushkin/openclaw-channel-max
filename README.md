# openclaw-channel-max

Канал мессенджера [MAX](https://max.ru) для [OpenClaw](https://openclaw.ai).

> *A [MAX messenger](https://max.ru) channel plugin for OpenClaw. Lets an OpenClaw
> agent receive and answer messages in MAX. Docs below are in Russian —
> MAX is a Russian-market messenger.*

Готового канала для MAX в OpenClaw нет: в каталоге около трёх десятков
мессенджеров, MAX среди них отсутствует, в ClawHub тоже пусто. Этот плагин
закрывает пробел.

## Что умеет

- Два транспорта на выбор: **вебхук** (рекомендуется) и long polling.
  Вебхук включается одним параметром `webhookPublicUrl`.
- Приём текстовых сообщений и вложений: картинок, файлов, **голосовых**.
  Вложение скачивается и передаётся ядру — распознавание речи и разбор
  изображений делает сам OpenClaw.
- Ответы агента обратно в MAX (`POST /messages`), с разбиением по 4000 символов.
- Политики доступа `dmPolicy` (`pairing` / `allowlist` / `open` / `disabled`)
  и `allowFrom` — та же модель, что у штатных каналов OpenClaw.
- Несколько аккаунтов: `channels.max.accounts.<id>`; значения аккаунта
  перекрывают корневые.
- Токен из файла (`tokenFile`), чтобы не держать секрет в конфиге.
- Горячий перезапуск: правка `channels.max.*` поднимает только этот канал,
  не трогая остальные.

## Чего пока нет

- **Вебхук.** MAX рекомендует его для продакшена, а long polling помечает как
  средство разработки и ограничивает по скорости.
- **Быстрый ответ вебхуку.** Ответ мессенджеру держится открытым до конца
  разбора: если ответить раньше, область выполнения запроса закрывается и
  запуск агента отклоняется с `GatewayDrainingError`. Пока агент думает,
  MAX успевает прислать сообщение повторно — дубль отсекается по `mid`,
  но выглядит это некрасиво.
- **Медиа передаётся ядру через устаревшие поля контекста** (`MediaPaths`
  и соседние). Работает, но правильный путь — полный контракт приёма
  с массивом `media`.
- **Долговечная очередь входящих.** Курсор `marker` живёт в памяти процесса:
  после перезапуска канал стартует с текущего момента и не переигрывает историю.
- **Уведомление о сопряжении.** `pairing.notify` отправляет код через аккаунт
  по умолчанию; на практике проще подтверждать вручную через
  `openclaw pairing approve`.

## Требования

- OpenClaw 2026.8 или новее.
- Node.js 22.22+, 24.15+ или 25.9+.
- Бот в MAX и его токен.

## Установка

```bash
git clone https://github.com/<владелец>/openclaw-channel-max.git
cd openclaw-channel-max
npm install
npm run build
```

Установщик OpenClaw копирует каталог целиком, включая `node_modules`, поэтому
ставить нужно чистую выкладку. Это делает вспомогательный скрипт:

```bash
bash scripts/install-local.sh
```

Он собирает проект, раскладывает в отдельный каталог только то, что нужно
в рантайме, и вызывает `openclaw plugins install`. После установки перезапустите
шлюз, чтобы плагин загрузился:

```bash
openclaw plugins install <каталог-выкладки> --force --accept-capabilities
systemctl restart openclaw-gateway   # или как у вас запускается шлюз
```

Флаг `--accept-capabilities` обязателен: плагин объявляет канал, а это требует
явного согласия.

## Получение токена

Бот создаётся в самом мессенджере у `@MasterBot`: команда `/create`, имя от 11
до 60 символов с обязательным окончанием `_bot`. В ответ приходит токен.

## Настройка

```jsonc
{
  "channels": {
    "max": {
      "tokenFile": "/путь/к/секретам/max.token",
      "dmPolicy": "allowlist",
      "allowFrom": ["<ваш user_id в MAX>"],
      // Публичный адрес шлюза. Задан — работаем вебхуком.
      // Без него голосовые приходить не будут, см. ниже.
      "webhookPublicUrl": "https://oc.example.org"
    }
  }
}
```

Или через CLI:

```bash
openclaw config set channels.max.tokenFile /путь/к/секретам/max.token
openclaw config set channels.max.dmPolicy allowlist
openclaw config set channels.max.allowFrom '["<ваш user_id>"]'
```

### Вебхук

Задайте `webhookPublicUrl` — публичный адрес, по которому доступен шлюз
OpenClaw. Канал сам зарегистрирует маршрут и подписку:

```
https://<ваш адрес>/max/webhook/<аккаунт>/<секрет>
```

Секрет выводится из токена бота, поэтому стабилен между перезапусками и не
требует хранения. MAX запросы не подписывает, так что незнание пути —
единственная защита от посторонних POST'ов; путь автоматически исключается
из авторизации шлюза.

Подписка переустанавливается при каждом старте: MAX отписывает бота после
восьми часов без успешных ответов, а старые подписки копит вместо замены.
Канал сначала снимает все прежние, потом регистрирует свою.

Без `webhookPublicUrl` канал работает опросом — проще в настройке, но
**голосовые приходить не будут**.

### Как узнать свой user_id

Он **не совпадает** с номером аккаунта, под которым создавался бот (тот зашит
в имя бота вида `seNNNNNNNN_1_bot`). Bot API оперирует другим идентификатором.

Самый простой способ: оставить `dmPolicy: "allowlist"` с пустым списком,
написать боту и посмотреть журнал шлюза — отказ печатает id отправителя:

```
[max] отправитель 200000002 отклонён политикой allowlist
```

Этот номер и нужен в `allowFrom`.

### Маршрутизация на агента

Если у вас несколько агентов, канал нужно привязать явно, иначе ядро откажется
угадывать (`AgentSelectionRequiredError`). Привязки живут в верхнеуровневом
массиве `bindings`:

```jsonc
{
  "bindings": [
    {
      "type": "route",
      "agentId": "<имя агента>",
      "match": { "channel": "max", "accountId": "default" }
    }
  ]
}
```

Правка `bindings` требует полного перезапуска шлюза.

### Несколько ботов

```jsonc
{
  "channels": {
    "max": {
      "dmPolicy": "allowlist",
      "accounts": {
        "default": { "tokenFile": "/путь/к/секретам/max-1.token",
                     "allowFrom": ["111"] },
        "support":  { "tokenFile": "/путь/к/секретам/max-2.token",
                      "allowFrom": ["222"] }
      }
    }
  }
}
```

Значения аккаунта перекрывают корневые, корневые служат общими умолчаниями.

## Параметры

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `token` | — | Токен бота прямо в конфиге. Предпочтительнее `tokenFile`. |
| `tokenFile` | — | Путь к файлу с токеном. |
| `apiBaseUrl` | `https://platform-api.max.ru` | База Bot API. |
| `dmPolicy` | `pairing` | Кто может писать боту в личку. |
| `allowFrom` | `[]` | Белый список отправителей. |
| `groupPolicy` | `allowlist` | Политика для групповых чатов. |
| `webhookPublicUrl` | — | Публичный адрес шлюза. Задан — вебхук, иначе опрос. |
| `pollTimeoutSec` | `30` | Таймаут одного запроса long polling (0–90). |
| `pollLimit` | `100` | Сколько событий забирать за раз (1–1000). |
| `enabled` | `true` | Выключатель аккаунта. |

## Вложения и голосовые

Формы входящих вложений в документации MAX нет — ниже то, что подтверждено
на живом боте.

**Картинки и файлы приходят полноценно, с прямой ссылкой:**

```jsonc
// изображение
{ "type": "image",
  "payload": { "photo_id": 500000000005, "token": "…", "url": "https://i.oneme.ru/i?r=…" } }

// файл
{ "type": "file", "filename": "ticket.pdf", "size": 367884,
  "payload": { "fileId": 600000000006, "token": "…",
               "url": "https://fd.oneme.ru/getfile?rq=…&expires=1791134734010" } }
```

`payload.url` скачивается напрямую; у файлов ссылка со сроком годности
(`expires`). Канал забирает вложение и передаёт агенту.

Скачивать нужно через `saveRemoteMedia` из
`openclaw/plugin-sdk/media-runtime`, а не самому: файл должен попасть
в каталог `media/inbound`, иначе инструмент просмотра изображений отвергнет
путь с ошибкой `Local media path is not under an allowed directory`. Хелпер
заодно определяет тип по содержимому — это важно, потому что MAX отдаёт
документы как `application/octet-stream`.

**Голосовые сообщения теряются при long polling — но приходят через вебхук.**

Это, пожалуй, главная грабля MAX Bot API. Одно и то же голосовое сообщение
доставляется по-разному в зависимости от канала доставки.

Через `GET /updates` приходит пустая оболочка — ни отправителя, ни чата,
ни вложения:

```json
{ "timestamp": 1788590646540, "user_locale": "ru", "update_type": "message_created" }
```

Через вебхук то же самое сообщение приходит целиком:

```jsonc
{ "update_type": "message_created",
  "message": {
    "sender":    { "user_id": 200000002, "first_name": "…" },
    "recipient": { "chat_type": "dialog", "chat_id": 300000003, "user_id": <бот> },
    "body": { "mid": "…", "text": "",
              "attachments": [
                { "type": "audio",
                  "payload": { "id": 400000000004, "token": "…",
                               "url": "https://a.oneme.ru/audio?cid=…&signatureToken=…" } }
              ] } } }
```

Файл по ссылке — **Ogg Opus, моно, 48 кГц**, тот же контейнер, что у голосовых
в Telegram, и он без вопросов скармливается любому распознавателю речи.

Воспроизводится стабильно: проверено на одном и том же сообщении в обе стороны.
В документации MAX об этом ничего нет. Практический вывод: **если вам нужны
голосовые — только вебхук**, на опросе они будут молча пропадать, и по событию
даже не удастся понять, кто написал.

Текстовые сообщения и остальные вложения при этом через опрос приходят
нормально.

## Особенности MAX Bot API, на которые стоит заложиться

- **Отвечать нужно в `recipient.chat_id`.** В диалоге `recipient.user_id` — это
  сам бот, то есть получатель входящего. Отправка по нему возвращает
  `Invalid chatId: 0`, и ответ теряется. `chat_id` работает и для диалога,
  и для группы.
- **`GET /chats` для ботов не отдаёт JSON** — приходит zip-архив с `logcat.txt`.
  Список диалогов через него получить нельзя.
- **`marker` в `/updates`** при первом запросе без значения отдаёт только
  последнее событие, а не всю очередь.
- **Подписка на вебхук и опрос взаимно исключают друг друга.** Пока подписка
  активна, `/updates` событий не отдаёт.
- **Подписки копятся, а не заменяются.** Перед регистрацией новой удаляйте
  старые, иначе получите дубли доставки.
- **Загруженное медиа обрабатывается не мгновенно.** Первая отправка
  сообщения с только что загруженным вложением возвращает
  `attachment.not.ready` — нужен повтор с небольшой задержкой.
- **`GET /messages` возвращает только сообщения самого бота.** Дозапросить
  входящее сообщение по нему нельзя.
- **Фильтр `types` в `/updates` отсекает молча.** При отладке лучше убрать его
  и логировать всё подряд, иначе неожиданные события исчезают бесследно.
- **Лимиты:** 30 запросов в секунду на REST, не больше двух сообщений в секунду
  в один диалог, 4000 символов на сообщение.
